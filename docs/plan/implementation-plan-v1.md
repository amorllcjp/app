# 日本版Context Bridge 実装計画 v1

作成日: 2026年8月3日
対象要件: [日本版Unabyss 要件定義書 v2](../requirements/unabyss-japan-requirements-v2.md)
ステータス: レビュー待ち（未着手）

## 0. この計画の位置づけ

要件定義書 v2 §17「採用する判断」を、実際の作業順序と合格条件に落とすための文書である。

- 要件書が「何を作るか / 何を作らないか」を決める。この計画は「どの順で作り、どこで止まるか」を決める。
- 要件書 F-18 に従い、**週数で管理しない**。マイルストーンごとの完了条件(DoD)で管理する。
- この計画を更新するトリガー: 要件書§16のレビュー・トリガー、または本計画§9の停止条件に該当したとき。

## 1. 計画の原則

1. **縦に1本通してから横に広げる。** Markdownだけで「取り込み → 索引 → 検索 → 出典 → エクスポート」を完成させる。ソースを増やすのはその後。
2. **価値の核をトランスポートより先に作る。** MCPは後から被せる層として扱う。MCPが壊れても価値の核が残る構造にする。
3. **各マイルストーンは、動く成果物と反証可能な合格条件を持つ。** 「実装した」ではなく「測って合格した」で進む。
4. **合格条件を満たさないときは、機能を足さずに範囲を削る。** これは要件書§12.3・§17と同じ規律である。
5. **未確認事項を要件へ昇格させない。** コード上も「未確認」「仮」が分かる形で残す。

## 3. 技術選定（提案）

決定ではなく提案である。ADRとして記録し、M1終了時に実測をもとに見直す。

| 領域 | 提案 | 根拠 | 覆す条件 |
|---|---|---|---|
| 言語 / 実行環境 | TypeScript / Node.js 22 LTS | MCP公式SDKがTypeScript。サーバーとコネクタを一言語で保守できる | チームの主言語が異なる場合 |
| HTTPサーバー | Fastify | Streamable HTTP のストリーミング応答を扱いやすく、素のNode HTTPに近い | SDK v2 が別の前提を要求する場合 |
| 永続化 | PostgreSQL 16 | 関係データ・全文検索・ベクトルを1系統で始められる。運用対象を増やさない | 検索品質がPostgresで出ない場合 |
| **日本語全文検索** | **pg_bigm または PGroonga**。M1で両方を同じ評価セットで比較しADR化 | PostgreSQL標準の `to_tsvector` は日本語を語分割できず、**要件書§7.4の「1. 語検索」を満たせない**。ここは選定を後回しにできない | どちらも精度不足なら Meilisearch / OpenSearch(kuromoji) を別系統として追加 |
| ベクトル検索 | pgvector。**必要範囲だけ**、M1では既定オフ | 要件書§7.4は語検索を先に置く。埋め込みは本文の外部送信を伴うため後段 | 語検索だけで評価目標に届かない場合に有効化 |
| ジョブ | pg-boss | Redis等を増やさずに冪等性・再試行・失敗状態・キャンセルを持てる（要件書§7.3ジョブ層） | 同期量が想定を超えた場合 |
| 秘密情報 | KMSによるエンベロープ暗号化。トークンは `token_ref` 経由でのみ参照 | 要件書 FR-002 / §10.1 | — |
| ホスティング / データ所在地 | **未決**（§8 D-2） | 要件書§10.2により、全委託先・バックアップ・ログ経路を確認する前に約束できない | — |

P0で明示的に採用しないもの: 専用ベクトルDBの別立て、LLMによる前処理、知識グラフ、ワークフローエンジン、マイクロサービス分割。

## 4. リポジトリ構成（M1着手時に作る）

```
/docs
  /requirements   要件定義書
  /plan           本計画
  /adr            決定記録
/apps
  /api            Web管理画面用API、認証、Pack/Policy
  /mcp            MCP Gateway（Streamable HTTP）
  /web            最小の管理画面
/packages
  /core           Pack、正規化、出典、由来、権限判定（トランスポート非依存）
  /search         語検索・意味検索の抽象と実装
  /connectors     markdown / notion / chatwork
  /audit          監査イベント
/eval             評価質問セット、実行スクリプト、結果履歴
/compat           クライアント互換テストの手順と記録
```

`packages/core` は MCP にも HTTP にも依存させない。要件書 FR-015 が示す互換性の問題を、価値の核から隔離するためである。§2で確認したとおりSDK v2は公開1週間であり、この隔離は形式ではなく実利のためのものである。

## 5. マイルストーン

各マイルストーンは、DoDを満たすまで次へ進まない。期間は書かない。

### M0: 土台とSpike（Gate 0 と並行）

目的: 実装を始める前に、崩れると計画全体を書き直すことになる前提を2つ潰す。

- **M0-1** リポジトリ初期化、CI（型チェック・lint・テスト）、ADR置き場、評価セットの器
- **M0-2 MCP v2 Spike** — `@modelcontextprotocol/server@2.0.0` でツールを1つ公開し、Streamable HTTP で応答させる
- **M0-3 クライアント接続Spike** — そのSpikeサーバーに Claude系 / Cursor から実際に接続し、ツール一覧・呼び出し・エラーを確認
- **M0-4 v1フォールバックSpike** — `@modelcontextprotocol/sdk@1.30.0` で同じSpikeが通ることを確認
- **M0-5** Gate 0 のインタビュー設計と実施開始（15件）

DoD:

- Spikeサーバーに、少なくとも1つのP0クライアントが認証して接続し、ツールを呼べる
- 接続できたクライアント名・バージョン・OS・認証方式・検証日を `/compat` に記録した
- v1系でも同じSpikeが通ることを確認した（退避経路の存在確認）
- §2.1の3点を要件書へ反映した

**要件書§14への提案変更**: 要件書はMCPの実機確認を3番目に置いている。しかし§2のとおりSDK v2は公開1週間であり、ここが崩れると§7.1全体を書き直すことになる。**Spikeだけを最初に前倒しし、本実装の順序は§14のまま維持する**ことを提案する。M1の実装内容は変更しない。

失敗時の縮退: v1系で実装し、v2移行を別計画にする。両方だめなら Markdownエクスポート中心（要件書§5.1 案A）へ縮退する。

### M1: Markdownだけで縦に1本通す（MCPなし）

目的: 価値の核を、外部APIとトランスポートの不確実性なしに完成させる。

対象FR: FR-001, FR-003(Markdown), FR-004, FR-006(Web内), FR-007, FR-008, FR-009, FR-011, FR-012, FR-013

- 個人ワークスペース、Pack の作成・更新・無効化、保持期間
- Markdown / 貼り付けの取り込み、正規化、チャンク分割
- 出典・作成/更新時刻・取得時刻・由来の保持（FR-007の全項目）
- 日本語語検索。**pg_bigm と PGroonga を同じ評価セットで比較し、ADRとして決着させる**
- 出典を持たない結果は検索結果に出さない
- 明示保存フロー（保存対象・Pack・保存者・保存理由の確認画面）
- Markdownエクスポート（出典URL・更新時刻・Pack名・注意事項を含む）
- 監査イベント記録。本文とトークンは書かない
- 上限値（Pack数、取得件数、抜粋長、総トークン量）

DoD:

- 評価セット（この時点で50問以上）で、正しい根拠がTop-5に入る割合を**測定して記録**できる
- 出典のない結果が1件も返らないことをテストで保証している
- エクスポート内容と検索結果の出典が一致する
- 日本語全文検索の方式がADRで決着している

### M2: MCP Gateway と P0クライアント（Gate 2）

対象FR: FR-006, FR-014, FR-015、要件書§7.1

- Streamable HTTP、2026-07-28系を主実装
- 認可: OAuth/OIDC ディスカバリ、PKCE、issuer検証
- **ステートレス前提**。`initialize` / `Mcp-Session-Id` を唯一の正常系にしない。状態は `pack_id` / `cursor` / `request_id` で持つ
- P0ツールは5種のみ（`context_search` / `context_get_evidence` / `context_pack_status` / `context_save` / `context_export`）
- ツール定義と入力スキーマのバージョン管理
- 外部ソース由来テキストを未信頼データとして明示ラベル（FR-014）
- v1系クライアントの互換テスト

DoD: 要件書§12.1の 1・3〜7、§12.2の 7。互換性マトリクスには、FR-015の「対応済み」定義（ツール一覧・認証・検索・エラー・長文・タイムアウト・再接続を通過）を満たしたクライアントのみ記載する。

### M3: Notionコネクタ（Gate 1 前半）

対象FR: FR-002, FR-003, FR-005, FR-010

- OAuth、ページ / データベース単位の選択、差分取得、削除検出、トークン失効、レート制限、ページング
- 同期状態6種の表示（未同期 / 同期中 / 完了 / 一部失敗 / 期限切れ / 権限失効）
- ソースごとの最終成功時刻、対象件数、失敗件数、次回試行
- 接続解除時の削除範囲表示と実行

DoD: 実アカウント2件以上で、更新・削除・権限剥奪が索引へ伝播し、**伝播完了までの時間を測定して表示できる**。要件書§12.2の 1・2。

### M4: Chatwork判定（Gate 1 後半）

**まず作らない。条件を確認する。** §2のとおり、現時点でChatworkのAPI条件は未確認である。

- アプリ登録の可否、OAuth、必要スコープ、ルーム / メッセージ取得、利用規約、レート制限、法人契約の要否
- 成立 → コネクタを実装（M3と同じDoD）
- 不成立 → **MVPを Notion + Markdown に縮退し、要件書§6.1を改訂する**

DoD: 成立 / 不成立のいずれかを、根拠つきで文書化して決定した。

### M5: 安全性・権限・削除（Gate 3）

対象FR: FR-010, FR-011, FR-012, FR-014、要件書§7.6・§10

- 攻撃テスト: 別ワークスペースの `pack_id` 指定、権限のないオブジェクト、失効後の検索、削除後の残存時間
- Prompt Injection: 取り込んだ本文からツール実行・権限昇格・外部送信を試みる攻撃セット
- 削除の完了条件を対象別（索引・キャッシュ・バックアップ・ログ・委託先）に定義し表示する

DoD: 要件書§12.3の「別ワークスペースのデータ漏えい0件」「出典付与率95%以上」、評価セット100問でTop-5 80%以上。**未達なら機能追加を止め、範囲を削る。**

### M6: パイロット（Gate 4）

- デザインパートナー3社、実データ、週次利用
- 測るもの: 接続から最初の検索までの完了率、再説明の削減、検索の空振り率、同期の滞留時間、OAuth失効率、1社あたりの費用

DoD: 要件書§12.3の残り。有償パイロット1社の意思表明。

### M7: 昇格を1つだけ選ぶ

GitHub App / Google Calendar / ChatGPT / Codex から、Gate 4 の結果に基づき **1つだけ** 昇格させる。同時に2つ着手しない（要件書§14-8）。

## 6. 最初に着手するタスク（M0の粒度）

1. リポジトリ初期化。TypeScript / Node 22、lint / format / test、CI
2. ADR-0001「MCP SDKのバージョンとパッケージ」— 本計画§2の確認結果を記録
3. ADR-0002「日本語全文検索の候補と評価方法」— pg_bigm / PGroonga の比較条件を先に決める
4. MCP v2 Spikeサーバー（ツール1つ、Streamable HTTP）
5. `/compat/README.md` — クライアント接続記録のテンプレート（FR-015の項目に一致させる）
6. v1系フォールバックSpike
7. 評価セットの器（質問、期待される根拠、対象Pack、実行日、検索バージョン）
8. Gate 0 インタビューの設問。要件書§13の失格条件（「便利そう」以外の具体的な業務損失）を判定できる形にする

## 7. 検証の仕組み

- **評価セットはM1から存在させ、M5で100問にする。** 後から作らない。後から作った評価セットは、実装に都合よく歪む。
- 各実行で「検索対象、取得時刻、検索バージョン、結果」を保存し再現可能にする（要件書§11.1）
- **権限テストとPrompt InjectionテストはCIで毎回動かす。** 人手のレビューに依存させない
- 互換性マトリクスは、クライアントやプロトコルの変更時に自動で「要再検証」へ戻せるようにする（FR-015）

## 9. この計画の停止条件

要件書§16のレビュー・トリガーに加えて、計画固有のものを置く。

- M0で、P0クライアントのどれもSpikeサーバーに接続できない
- MCP SDK v2 に回避不能な破壊的変更または重大不具合があり、v1でも要件を満たせない
- M1で、日本語語検索がどの候補でも評価目標に届かない
- M4でChatworkが不成立、かつ「Notion + Markdown だけでは Gate 0 の課題を解けない」とインタビューが示す

いずれの場合も、**機能を足して回復させない**。範囲を削るか、要件書§17の判断へ戻す。
