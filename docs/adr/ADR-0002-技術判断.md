# ADR-0002: 技術判断（検索・MCP・認証）

日付: 2026-08-03（2026-08-04 に PostgreSQL 移行を反映）
状態: 採用

## 1. 日本語検索を自前のbigram索引で行う

### 測定した事実

| 方式 | 「請求書」(3文字) | 「単価」(2文字) | 「田中」(2文字) |
|---|---|---|---|
| PostgreSQL `to_tsvector('japanese'相当なし)` に原文をそのまま入れる | 語分割できず不可 | 不可 | 不可 |
| SQLite FTS5 `trigram` トークナイザ | ヒット | **0件** | **0件** |
| **自前bigram索引 + 実体再チェック**（SQLite / PostgreSQL 共通） | ヒット | ヒット | ヒット |

原文をそのまま Postgres の全文検索に入れても日本語は語分割されない。
しかし**こちらが先に bigram へ分割してから渡せば**、`simple` 設定は空白で区切るだけなので
bigram がそのまま lexeme になる。PGlite（Postgres 18）で実測して確認した。

FTS5 の `trigram` は3文字のグラムを作るため、2文字のクエリからはグラムが1つも生成されず、
何にも一致しない。日本語の業務語は2文字が多い（単価、面談、請求、稟議、検収）ため、
これは実運用で致命的になる。

### 採用した方式

pg_bigm と同じ二段構えにした。

1. 本文を2文字の重なりグラムに展開して索引に入れる（FTS5 / tsvector）
2. クエリも同様に展開し AND で候補を引く
3. **候補の原文に対して、クエリ文字列そのものを含むか再チェックする**

3 が無いと「東京」「京都」を含むが「東京都」とは書かれていない文書が誤ってヒットする。
この偽陽性はテストで固定している（`test/core.test.ts`）。

### 結果

**この方式は SQLite と PostgreSQL の両方で成立する。** そのため PostgreSQL へ移行しても
検索ロジックの考え方は変わらず、格納先が FTS5 仮想テーブルから `tsvector` + GIN に変わっただけで済んだ。

`pg_bigm`、`PGroonga`、`pgvector` はいずれも不要。Neon の標準構成で動く。
これによりホスティング先の選択が拡張の対応状況に縛られなくなった。

副次的な改善: SQLite 版では索引が別テーブル（FTS5 仮想テーブル）だったため、
チャンクを消して索引を消し忘れると削除済みの内容が検索に残る危険があった。
PostgreSQL では `tsvector` を `chunks` の同じ行に持てるので、**この種のバグが構造的に消えた**。

### 見直す条件

- 語検索での正解率が評価セットで目標に届かない

## 2. MCP は SDK v2 を使い、両世代を1つの定義で serve する

### 確認した事実

- v2 のパッケージ名は `@modelcontextprotocol/server` / `@modelcontextprotocol/client`（各 2.0.0）。
  従来の `@modelcontextprotocol/sdk` は 1.30.0 が最新で 2.x は存在しない
- `createMcpHandler` の既定 `legacy: 'stateless'` により、**2025系クライアントと
  2026-07-28系クライアントの両方が、同じツール定義で動く**

### 実機で確認した動作

| 世代 | リクエスト形式 | 結果 |
|---|---|---|
| 2025系 | 通常の JSON-RPC POST | 動作 |
| 2026-07-28系 | `MCP-Protocol-Version` + `Mcp-Method` + `Mcp-Name` ヘッダ + `params._meta` エンベロープ | 動作 |

2026-07-28系は、ヘッダとボディの整合を厳密に検査する。ヘッダが欠けると
`-32020 Bad Request` を返し、何が足りないかを名指しで教えてくれる。

### 意味

要件書 §7.1 が想定していた「旧クライアント互換を別途作る」作業は不要だった。
互換性マトリクス（FR-015）は、実際に接続したクライアントの記録として引き続き必要。

## 3. MCP認証は Bearer トークンにする（要件書からの意図的な逸脱）

### 逸脱の内容

要件書 §7.1 は「OAuth/OIDC のディスカバリ、PKCE、issuer検証を満たす実装」を求めている。
MVPではワークスペース単位の Bearer トークンにした。

### 理由

Bearer でも、検証したいこと（クライアントが繋がるか／課金が成立するか）は検証できる。
OAuth 一式は実装量が大きく、それを先に作ると最初の顧客に会うのが遅れる。

### 現状の防御

- トークンの平文は保存せず SHA-256 ハッシュのみ保持。発行時に一度だけ表示
- 再発行で旧トークンは即時失効（テストで固定）
- トークンはワークスペースに束縛。他ワークスペースは一切見えない（テストで固定）
- 認証できないリクエストにはツール一覧すら返さない（401）

### 返済条件

以下のいずれかで OAuth に移行する。

- 複数人で1ワークスペースを使う要求が出た（トークン共有が起きる）
- 顧客のセキュリティレビューで OAuth が要件として提示された
- MCPクライアント側が Bearer ヘッダ設定を廃止した

## 4. 保存は PostgreSQL（本番 Neon / ローカルとテスト PGlite）

### 経緯

当初は SQLite 単一ファイルで実装した。デプロイ先を Vercel に決めたため変更した。
Vercel はサーバーレスで永続ディスクを持たず、ファイルベースの SQLite が原理的に使えない。

### 採用

| 用途 | 実装 |
|---|---|
| 本番 | Neon（`DATABASE_URL`）。`@neondatabase/serverless` 経由 |
| ローカル開発・テスト | PGlite（Postgres の WASM ビルド）。`DATABASE_URL` 未設定時に自動で使う |

`src/db.ts` の `Sql` インターフェースが driver の差を吸収する。SQL の方言は1つだけ。

### テストにモックを使わない

PGlite は本物の Postgres なので、テストと本番で SQL の挙動が変わらない。
Docker も外部サービスも不要で、`npm test` がどこでも走る。
テスト26件はすべて PGlite 上で通っている。

### Vercel 固有の注意

- Neon は**必ず pooled 接続（`-pooler` 付き）を使う**。サーバーレスは同時実行が増えると
  DB接続を食い潰すため、直結にしない
- マイグレーションは cold start では走らせない。`npm run migrate` でデプロイ時に一度だけ実行する

### 見直す条件

- 検索が遅くなり、GIN索引だけでは足りなくなった時
- Neon の従量課金が想定を超えた時（その場合も SQL は変えずに移せる）

## 5. なぜ Vercel を選んだか

Fly.io（永続ボリューム + SQLite 継続）や Cloudflare Workers + D1 も検討した。
D1 は FTS5 が使えることをローカルで確認しており、技術的には成立する。

決め手は**運用者がすでに Vercel と Neon の実運用経験を持っていること**。
障害時に復旧できるかは、プラットフォームの構造的優劣より効く。
Fly.io の実質的な利点は「SQLite をそのまま置ける」ことだけで、
ホスト型DBを使う時点でその利点は消える。

見直す条件: Vercel の実行時間上限やコストが問題になった時。
その場合も `src/app.ts` は実行環境に依存しないので、エントリだけ差し替えれば移せる。
